# 公式速查 · Shader 数学

> **用法**：这份表随每段学习追加。做题卡住时先查这里，**不要背**——目标是理解几何意义，
> 而不是记住符号。
>
> 记号约定：`a`、`b`、`n`、`L` 都表示**向量**（`float3`/`half3`）；`θ` 表示两向量夹角；
> 点乘写作 `dot(a, b)`，在 HLSL 里就是内置函数。

## T0.2 · 首次接触（光照的起点）

### normalize(v) —— 归一化：保持方向，把长度压成 1

```text
|v|         = √(v.x² + v.y² + v.z²)              向量长度（勾股定理的三维版）
normalize(v) = v / |v|                            长度变 1，方向不变

例：v = (3, 4, 0)
    |v| = √(9 + 16) = 5
    normalize(v) = (0.6, 0.8, 0)                  长度 = 1
```

**关键性质**

```text
normalize(normalize(v)) == normalize(v)           归一化是幂等的，做一次就够
```

**什么时候必须用**：任何要参与 `dot` 的向量，**长度必须都是 1**。理由见下面的点乘。

**为什么不能省**：法线从网格取出来时长度的确接近 1，但**经过矩阵变换后长度会变**（缩放会改变长度，
非等比缩放还会改变方向关系）。变换完要归一化回来。

---

### dot(a, b) —— 点乘：把「两个向量的夹角关系」压成一个数

**代数定义**（计算机实际算的）

```text
dot(a, b) = a.x*b.x + a.y*b.y + a.z*b.z          对应分量相乘，然后全部相加
```

结果是一个**标量**（单个数字），不是向量。

**几何定义**（理解用）

```text
dot(a, b) = |a| · |b| · cosθ
```

**当 a、b 都已归一化时**（`|a| = |b| = 1`），公式退化成：

```text
dot(a, b) = cosθ                                  ← 这就是为什么要先归一化
```

于是结果只反映**角度关系**：

| 两向量关系 | θ | cosθ = dot |
|---|---|---|
| 完全同向 | 0° | **+1** |
| 垂直 | 90° | **0** |
| 完全反向 | 180° | **−1** |
| 有夹角但同向侧 | 0<θ<90° | 0 ~ +1 |
| 有夹角但反向侧 | 90°<θ<180° | −1 ~ 0 |

**光照里为什么用它**

「表面朝向」和「光照方向」的关系，本质就是**同向还是反向**：

```text
N 指向上方、光也朝上照  → N 和 L 同向  → dot = +1 → 最亮（光垂直打在表面）
N 指向侧面、光平行掠过  → N 和 L 垂直  → dot =  0 → 无光（Lambert 模型下）
N 指向下方、光在上方    → N 和 L 反向  → dot = −1 → 最暗
```

**这是一切光照模型的地基。** `half ndotl = saturate(dot(N, L));` 就是 Lambert 漫反射的完整核心。

### saturate(x) —— 饱和：把值压进 [0, 1]

```text
saturate(x) = clamp(x, 0, 1)                     简写关系

3.0  → 1.0
-1.0 → 0.0
0.6  → 0.6                                       区间内的值原样不动
```

**这是钳制（clamp），不是归一化**

| 操作 | 行为 | 区间内的值 |
|---|---|---|
| **钳制** clamp | 越界的压到边界 | **不变** |
| 归一化 normalize | 整体缩放 | **也变** |

判据：**看区间内的值有没有被动过**。`0.6` 没有被改成别的数 → 是钳制。

**为什么光照里要用它**

背光侧 `dot(N, L)` 算出**负数**，而颜色通道不接受负值。两种处理方式的差别：

```text
❌ 不钳：负值一路往下传，后面加高光、乘颜色时污染整条计算链，
        最后靠帧缓冲隐式钳掉——但你无法控制中间过程发生了什么
✅ 就地 saturate：值域当场收敛到 [0, 1]，后面拿到的永远是干净数据
```

**纪律**：把值域问题就地解决，不要指望最后那道隐式钳制兜底。

### TransformObjectToWorldNormal(n) —— 法线：模型空间 → 世界空间

```text
n_world = normalize( (M⁻¹)ᵀ · n_local )
                    └─ M 的逆转置
```

**为什么是逆转置，而不是直接乘 M**

```text
点的变换：  p_world = M · p_local                ← 直接用 M
法线的变换：n_world = (M⁻¹)ᵀ · n_local            ← 必须用逆转置
```

原因（**结论先记住，阶段 1 会专门推一遍**）：法线描述的是「**朝向**」，
而 `M` 描述的是「顶点位置怎么被搬运」。当有**非等比缩放**（例如把球压扁）时：

```text
直接用 M 变换法线 → 法线会偏离表面真正的垂直方向 → 光照变歪
用 (M⁻¹)ᵀ 变换    → 法线始终保持与表面垂直
```

**为什么必须统一坐标系**

`dot(N, L)` 只有在 **N 和 L 位于同一个坐标系**时才有意义。光源方向是世界空间的量，
所以法线也必须搬到世界空间——否则算出来的是无意义的数字。
（URP 里用 `TransformObjectToWorldNormal` 一步到位。）

### _MainLightPosition —— 主光方向（URP 全局变量）

URP 提供的全局量，装场景主光（Directional Light）在世界空间的方向。

**它属于「整个物体内都不变的量」**，所以在**顶点阶段**取一次即可：

```text
整个物体内都不变的量 → 顶点阶段算一次（省）
每个像素都不同的量   → 片元阶段算（准）
```

T0.2 骨架里的分配就是这个道理：

```text
normalWS   每个像素都不同  → 在片元阶段 normalize
lightDirWS 全物体都一样    → 在顶点阶段取一次，通过 Varyings 传下去
```

**方向约定（2026-10-12 从 URP 源码核实）**：它装的是**从表面指向光源**的方向，也就是标准光照公式里的 `L`。

证据链（都在本机包里，可自己查）：

```text
Runtime/UniversalRenderPipelineCore.cs  第 1837 行
    Vector4 dir = -lightLocalToWorld.GetColumn(2);     ← 负号在这里
    （GetColumn(2) 是光源的 forward 轴 = 光传播方向；取负后变成「指向光源」）
        ↓
ShaderLibrary/RealtimeLights.hlsl       第 84 行
    light.direction = half3(_MainLightPosition.xyz);   ← 原样交出去
```

所以 `dot(N, L)` 在受光面为正，Lambert 能直接套用。
**这个负号是人为约定**，不是数学必然——它存在只是为了让公式好用。

## T0.2 已验证（2026-10-12）

四条待验证项全部亲手验证完毕：

- [x] `dot(N, L)` = **+1** 在**正对光源**的那一点，= **−1** 在**背对光源**的那一点。
- [x] 不做 `saturate` 时，背光侧得到**负数**，写进颜色通道时被**截断成 0**，画面是**纯黑**。
- [x] 加上 `saturate` 后，两张截图**完全一样**——因为两边都是 0。
      （实测：x=299~323 共 352 个像素恒为 0，没有任何层次）
- [x] `_MainLightPosition` 是「**表面指向光源**」（见上一节，已从源码核实）。

### 三条要记住的

**① `dot` ≠ `cross`**

```text
dot(a, b)   → 一个数（标量）   ← 光照里的 N·L
cross(a, b) → 一个向量          ← T0.3 才学
自检办法：看结果有几个分量。一个数就一定是点乘。
```

**② 负值不是「灰色」，负值就是黑**

颜色通道只接受 0~1，负数在写入时被截断成 0：

```text
灰 = 接近 0 的正数（例如 +0.04）
黑 = 0 —— 既包括 0 本身，也包括所有负数
     （−0.05 和 −0.98 在屏幕上完全没有区别）
```

代价：**负值区内部的全部信息都丢了**。这就是为什么纪律要求「就地 `saturate`」，
而不是指望帧缓冲最后兜底——兜底只对最终画面有效，中间过程已经被污染了。

**③ 参与点乘的两个向量必须在同一个坐标系**

实测：球 = Rotation Y，光 `euler = (0,0,0)`，**只改球的旋转**，采样球面同一行 5 个点：

| 球的旋转 Y | 0° | 45° | 90° | 135° | 180° |
|---|---|---|---|---|---|
| 正确写法 `TransformObjectToWorldNormal` | 191 245 251 241 191 | 192 245 251 240 192 | 191 245 251 241 191 | 192 245 251 240 192 | 191 245 251 241 191 |
| 错误写法 `IN.normalOS` | 191 245 251 241 191 | 251 241 211 152 000 | 236 155 000 000 000 | 129 000 000 000 000 | 000 000 000 000 000 |

```text
正确写法：转 180° 画面最多差 1 个灰阶（浮点/光栅化噪声）
          → 光照只由「表面在世界空间的朝向」决定
错误写法：转 180° 整颗球从亮变成全黑
          → 光照被「物体自己的旋转」带着跑
```

⚠️ **做这个实验必须先让两个坐标系错开**：Rotation = 0 时两种写法**碰巧完全相同**
（物体坐标系与世界坐标系重合），在那里测会得出「这个函数没关系」的错误结论。

（注：上面说的「转动物体画面不变」是针对**球**这种旋转对称的物体。
换成立方体，转动物体**应该**改变画面，因为它的表面朝向真的变了——
「应该变」和「不该变」的区别，正是这个坐标系约定要保证的东西。）
